# 01 — Data Model

Database models, kobo precision rules, the booking state machine, and ledger design.

Implemented by issue **#4**. Everything here is authoritative for `apps/backend/prisma/schema.prisma`.

---

## 1. Precision rules

These are enforced mechanically by `npm run check:rules`, which greps the schema and fails the build on a violation.

1. **Every monetary field is `Int`, in kobo.** Field names carrying money end in `Kobo` so a violation is visible at a glance.
2. **`Float` and `Decimal` appear nowhere in the schema.** Not on money, not on rates, not on geolocation accuracy, not "just for this one field."
3. **Percentages are `Int` basis points.** 500 = 5%. 10000 = 100%.
4. **Day counts, weights and thresholds are `Int`.**
5. **Geolocation**, which is genuinely fractional, is stored as `String` (the raw decimal text as reported by the device) precisely so that no `Float` enters the schema. It is supporting metadata that is never computed on.

`VerificationStatus` separates `RETRYABLE_FAILURE` from `REJECTED` deliberately. A provider timeout is not a failed identity check, and collapsing the two would permanently lock a legitimate user out of the platform over a network blip. See `02` §6.

## 3. Models

### Identity

**`User`** — one row per person, whatever their role.

| Field | Type | Notes |
|---|---|---|
| `id` | `String` cuid | |
| `email` | `String` unique | |
| `phone` | `String` unique | E.164. Required — SMS is load-bearing (`04`, `06`) |
| `passwordHash` | `String` | bcrypt. Never plaintext, never reversible |
| `role` | `Role` | |
| `verificationStatus` | `VerificationStatus` | default `UNVERIFIED` |
| `verificationMethod` | `VerificationMethod?` | |
| `verifiedAt` | `DateTime?` | |
| `verificationReference` | `String?` | Provider's reference for the check. **Never the raw NIN or BVN** |
| `accountStanding` | `AccountStanding` | default `GOOD` |
| `restrictedMinLeadDays` | `Int?` | Set when standing is `RESTRICTED` (`06`) |

Relations: `artist Artist?`, `client Client?`, strikes, audit rows.

**`Artist`** — profile and rate card. `baseRateKobo Int` is validated against ₦20,000–₦3,000,000 at the application layer (`02` §4), not by a database constraint, so the error message can name the limit.

**`Client`** — display name and booking history. Thin by design; most client state lives on `User`.

### Transaction

**`Booking`** — the centre of the model.

| Field | Type | Notes |
|---|---|---|
| `amountKobo` | `Int` | The agreed fee |
| `eventDate` / `eventEndAt` | `DateTime` | `eventEndAt` gates confirmation (`04` §3) |
| `state` | `BookingState` | default `PENDING_PAYMENT` |
| `escrowReference` | `String` **unique** | **Self-generated by us**, never the provider's |
| `escrowId` | `String?` | The provider's id, recorded after create succeeds |
| `commissionRateBpsSnapshot` | `Int` | Frozen at creation |
| `cancellationTiersSnapshot` | `Json` | The **full** tier set, frozen at creation |
| `checkInCode` | `String?` | See §6 |
| `checkInCodeValidFrom` / `checkInCodeValidUntil` | `DateTime?` | |

The two snapshot fields are the mechanism that makes `07`'s versioning mean anything. **All payout and cancellation math reads the snapshot, never live configuration.** The tier set is stored as JSON because it is read as a unit and never queried by individual row.

**`CheckIn`** — the redemption record, one per booking.

`redeemedAt DateTime @default(now())`. There is **no client-writable timestamp field on this model.** A client-supplied time is an assertion, not evidence, and this record is the primary evidence in every subsequent dispute. Geolocation (`latitude`, `longitude`, `accuracyMeters` — all `String?`) is captured where available and never gates redemption.

**`Cancellation`** — one per cancelled booking. Records who initiated, how many days before the event, the **tier that was applied as a JSON copy**, and the resulting `clientRefundKobo`, `artistCompensationKobo`, `escrowFeesKobo` and `feeBearer`. Carries the reclassification fields used by #29 (`reclassifiedAsArtistFault`, `reclassifiedByUserId`, `reclassificationReason`, `reclassifiedAt`).

**`Dispute`** — state per `DisputeState`, the deciding admin, the mandatory `resolutionReason`, optional split amounts, and `externalMediatorOpinion` which is **informational only and executes nothing** (`04` §6).

**`DisputeEvidence`** — statements and files from either party.

> **Deviation flagged:** #4's model list does not name `DisputeEvidence`. It is included here because #31 requires both parties to attach evidence to the same dispute, and modelling that as a JSON blob on `Dispute` would make "who submitted what, when" unqueryable — which is precisely the question a dispute review asks. Defining it now costs one migration; adding it later costs a migration that contradicts an earlier one, which is the failure #4's own context argues against.

**`TermsAcknowledgement`** — one per booking. Stores `tiersAsDisplayed Json` and `commissionRateBpsAsDisplayed Int` — the **literal percentages shown to the client**, not a foreign key to a config version. A pointer requires reconstructing what the client saw; a copy *is* what they saw. This row is the FCCPA defence (`05` §7).

### Money

**`LedgerEntry`** — see §5. **Append-only.**

**`FeeLiability`** — an artist's unpaid fee obligation from a cancellation where there was no artist money to deduct from. Carries `amountKobo`, `originBookingId`, `status`, and `settledAgainstBookingId` once recovered from a later payout (`05` §6).

### Configuration

**`CommissionRate`** — `rateBasisPoints Int`, `effectiveFrom`, `setByUserId`, `createdAt`. **Append-only: a change writes a new row and never touches the old one.**

**`CancellationTier`** — one row per band, with rows sharing a `versionId` forming one tier set. `minDaysBefore Int`, `maxDaysBefore Int?` (null = open-ended top band), `clientRefundBps Int`, `artistCompensationBps Int`, plus `versionId`, `effectiveFrom`, `setByUserId`. A "new version" is a new group of rows; prior versions remain queryable forever.

**`Strike`** — `userId`, `trigger`, `weight Int`, `reason`, the triggering `bookingId`, and the admin override fields (`overriddenByUserId`, `overrideReason`, `overriddenAt`).

**`AuditLog`** — `actorUserId`, `action`, `entityType`, `entityId`, `reason`, `before Json?`, `after Json?`. Written for every configuration change, every dispute resolution, every manual money movement, and every strike override.

**`WebhookEvent`** — `providerEventId` **unique**, `eventType`, `rawBody`, `receivedAt`, `processedAt?`, `processingStatus`, `attempts`, `lastError?`. The unique constraint is the idempotency guarantee; see `03` §6.

## 4. Booking state machine

```
PENDING_PAYMENT ──────► FUNDED_HELD ──────► CHECKED_IN
       │                    │  │                 │
       │                    │  │                 ▼
       ▼                    │  └────────► AWAITING_CONFIRMATION
   CANCELLED ◄──────────────┤                    │
                            │                    ├────► RELEASED
                            ├────► REFUNDED ◄────┤
                            │                    │
                            └────► DISPUTED ◄────┘
                                      │
                                      ▼
                                  RESOLVED
```

The allowed-transition map, implemented explicitly in `bookingService.js`:

| From | Allowed to |
|---|---|
| `PENDING_PAYMENT` | `FUNDED_HELD`, `CANCELLED` |
| `FUNDED_HELD` | `CHECKED_IN`, `AWAITING_CONFIRMATION`, `CANCELLED`, `REFUNDED`, `DISPUTED` |
| `CHECKED_IN` | `AWAITING_CONFIRMATION`, `RELEASED`, `DISPUTED` |
| `AWAITING_CONFIRMATION` | `RELEASED`, `REFUNDED`, `DISPUTED` |
| `DISPUTED` | `RESOLVED` |
| `RELEASED`, `REFUNDED`, `CANCELLED`, `RESOLVED` | — terminal |

**An illegal transition throws.** It does not log a warning and proceed, and it does not silently no-op. On a money-bearing state machine, a transition that should be impossible arriving anyway means an assumption is wrong, and continuing past that point is how an unrecoverable state gets written.

## 5. Ledger design

The ledger answers the question booking state cannot: *how did the money get there.* That is the question a client, an artist, or a regulator actually asks, months later.

### Rules

1. **Append-only.** No `update`, no `delete`, anywhere in the codebase. Enforced by grep in `check:rules`.
2. **Corrections are new offsetting entries**, typed `CORRECTION` and referencing the entry they offset. The original stays visible, because the sequence — charged, then reversed, and why — is the record that matters.
3. **Written inside the same database transaction** as the state change they accompany. A state change without its ledger entry, or a ledger entry without its state change, is a reconciliation failure that is very hard to detect afterwards and impossible to reconstruct.
4. **Every entry names its booking and its bearing party.**

### Sign convention

`amountKobo` is **signed from the party's perspective**: positive means the party received value, negative means the party parted with it. **The entries for any settled booking sum to exactly zero.** That single invariant is the widest-catching financial check in the system, which is why `40`'s e2e script asserts it at the end of every scenario.

Worked example — a ₦200,000 booking completing at 5% commission:

| Type | Party | `amountKobo` |
|---|---|---|
| `FUNDED` | `CLIENT` | −20,000,000 |
| `COMMISSION` | `PLATFORM` | +1,000,000 |
| `ESCROW_FEE_IN` | `PROVIDER` | +200,000 |
| `ESCROW_FEE_OUT` | `PROVIDER` | +7,000 |
| `RELEASED` | `ARTIST` | +18,793,000 |
| | **Sum** | **0** |

The artist receives **₦190,000** and the client transfers **₦202,000**, which are the figures #26 asserts. The arithmetic behind each line is in `05` — including the correction found at #18, where the provider's live fee configuration turned out to charge money-in to the client at funding and money-out to the platform, rather than deducting both from the escrow. The figure recorded here was previously ₦187,930.
