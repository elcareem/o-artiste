# 03 — Escrow Flow

Fund lifecycle, the EscrowPay contract, webhook verification, and idempotency requirements.

---

## 1. The provider contract

EscrowPay exposes four calls plus webhooks. Wrapped by `lib/escrowpay.js` (#17), which is a **transport only** — no business logic, no ledger writes, no state transitions.

| Call | Purpose |
|---|---|
| `POST /v1/escrows` | Create a transaction, returns an id and a bank transfer funding instruction |
| `GET /v1/escrows/:id` | Current state |
| `POST /v1/escrows/:id/release` | Pay the artist |
| `POST /v1/escrows/:id/refund` | Return funds to the client |

Create payload:

```json
{
  "amount": 145000,
  "currency": "NGN",
  "buyer":  { "phone": "+234..." },
  "seller": { "phone": "+234..." },
  "reference": "our_own_reference",
  "terms": "Booking description"
}
```

Provider states: `created · funded · delivered · released · refunded · disputed`.

### Amount unit — open item 11.8

The provider's documented example shows `"amount": 145000` for a ₦145,000 transaction, which reads as **whole Naira**, while this codebase is kobo everywhere. The discrepancy is unresolved (`00` §11.8).

Handling: **one conversion point**, inside `lib/escrowpay.js`, gated on `ESCROWPAY_AMOUNT_UNIT`. When set to `naira` it asserts `amountKobo % 100 === 0` and **throws** on a fractional Naira rather than silently rounding. Nothing else in the codebase converts, so confirming the answer is a one-line change rather than an audit.

Getting this wrong creates escrows at 100× or 1/100 of the intended value. The ₦20,000–₦3,000,000 range check would catch a gross mismatch, which is a safety net, not a substitute for confirming.

## 2. Happy path

```
Client                Backend               EscrowPay            Artist
  │                      │                      │                   │
  ├── POST /bookings ───►│                      │                   │
  │                      ├── createEscrow ─────►│                   │
  │◄── funding instr. ───┤◄── escrow id ────────┤                   │
  │                                                                 │
  ├── bank transfer ────────────────────────────►│                  │
  │                      │◄── escrow.funded ─────┤                  │
  │                      │  state → FUNDED_HELD                     │
  │                      │  ledger: FUNDED                          │
  │                      │  schedule auto-release job               │
  │                                                                 │
  │                   [ event happens ]                             │
  ├── shows code ───────────────────────────────────────────────────►
  │                      │◄── POST /check-in ───────────────────────┤
  │                      │  state → CHECKED_IN, CheckIn recorded    │
  │                                                                 │
  ├── POST /confirm ────►│                                          │
  │                      ├── escrowService.release ──►│             │
  │                      │  state → RELEASED                        │
  │                      │  ledger: COMMISSION, FEES, RELEASED      │
  │                      │◄── escrow.released ───────┤              │
```

Note the ordering: **the state change and its ledger entries are written in one database transaction, and the provider instruction is what that transaction is recording.** The confirming `escrow.released` webhook that arrives afterwards is a reconciliation signal, not the thing that causes the state change.

## 3. Self-generated references

`escrowReference` is generated by us at booking creation and is unique across bookings. We never adopt the provider's identifier as our key.

This exists for exactly one reason: **retry safety.** A create call that times out leaves us not knowing whether an escrow exists. With our own reference, the retry is the same request — the provider recognises it and does not create a second escrow. With a provider-generated key we would have no way to ask "did my previous attempt land", and the failure mode is two escrows for one booking, one of which nobody is watching.

The provider's `escrowId` is recorded once create succeeds, and is used for subsequent calls.

## 4. Funding

**Bank transfer only. No card path may be implemented anywhere in this codebase**, and `check:rules` greps for one.

Escrow and card chargebacks are structurally incompatible: a chargeback can land weeks after funds have been released to an artist, and that money is unrecoverable. Adding a card path "just for convenience" reintroduces precisely the risk escrow exists to remove.

### Provider failure on create

If `createEscrow` fails, the booking **stays cleanly in `PENDING_PAYMENT` with no orphaned provider-side record.** A half-created booking is worse than a failed one: the client sees a booking that looks real, and there is money-shaped state on the provider's side that nothing in our system is tracking.

## 5. The single money-moving module

**Only `escrowService.js` may call the provider's `release` or `refund`.** No route handler, no job, no other service.

This is a structural guarantee, not a style preference. Release carries four obligations that must all happen together — apply the booking's snapshotted commission, apply fee-bearer rules, settle any outstanding `FeeLiability`, write the ledger entries in the same transaction. With one caller, that is verified once. With four callers it becomes a code-review problem, and code review does not catch the fifth caller added in a hurry six months later.

Enforced by grep in `check:rules` and re-verified at #41.

## 6. Webhooks — the highest-severity path

A webhook delivered twice and processed twice is a double release. Providers retry on timeout, on non-2xx responses, and sometimes on slow 2xx responses, so **duplicate delivery is expected behaviour, not an edge case.**

### Required order of operations

```
1. Read the RAW body — bytes exactly as received
2. Verify the signature against those bytes        → invalid: 401, write nothing, stop
3. Record the event id in WebhookEvent             → already present: 200, stop
4. Only now: process
5. Mark processed
```

Every step's position is load-bearing:

**Raw body, step 1.** Signature verification runs against the exact bytes received. `express.json()` parses and re-serialises, which changes key order and whitespace, and the signature no longer matches. The exception is configured in `src/index.js` at bootstrap (#2) rather than retrofitted, because without it the failure surfaces only during integration testing, and looks like a provider problem.

**Invalid signature writes nothing, step 2.** A rejected payload leaves **no `WebhookEvent` row**. Recording unverified events lets anyone who can reach the endpoint pre-poison the idempotency table with event ids that will then be ignored when they legitimately arrive.

**Recorded before processing, step 3.** Recording afterwards leaves a window: a crash mid-processing means the event is retried and reprocessed from scratch, with whatever partial work the first attempt did already committed.

### Behaviour

| Situation | Response |
|---|---|
| Valid, new event | `200`, processed |
| Valid, already-processed event id | `200`, **no further action** |
| Invalid signature | `401`, no row written |
| Unknown event type | `200`, logged — *not* rejected |
| Handler throws mid-processing | `200`, retry queued via BullMQ |

Unknown types are acknowledged because a non-2xx tells the provider to retry, and retrying an event we will never understand achieves nothing but noise. Log it and move on.

Processing failures go to the job queue. **A webhook is never silently dropped** — the event is recorded, so a failure is visible and replayable rather than lost.

### Handled events

`escrow.funded` · `escrow.released` · `escrow.refunded` · `escrow.disputed`

| Event | Effect |
|---|---|
| `escrow.funded` | → `FUNDED_HELD`, ledger `FUNDED`, schedule auto-release, notify both parties |
| `escrow.released` | Reconcile with the release we instructed; confirm `RELEASED` |
| `escrow.refunded` | Reconcile with the refund we instructed; confirm `REFUNDED` |
| `escrow.disputed` | Provider-side dispute signal; open or attach to a dispute |

## 7. Timeouts

The HTTP client timeout must sit **below the host's request timeout**, recorded in `DEPLOYMENT-CHECKLIST.md` at #2.

If the provider call outlives the request, the host kills the request while the call is still in flight — and an escrow may be created that we have no record of. Our own timeout firing first means we control what happens next, and the self-generated reference in §3 makes the retry safe.

## 8. Frontend isolation

**The frontend never communicates with EscrowPay.** No API calls, no SDK, no key in a `NEXT_PUBLIC_` variable. It talks to our backend and nothing else. Verified at #41.
